## 1. 질문 카테고리 상세

### 1.1 재사용할 기존 코드

**왜 물어야 하는가**: AI는 코드베이스의 전체 컴포넌트 목록을 기억하지 못한다. 탐색으로 발견해도, 사용자만 아는 제약(성능 이슈, deprecated 예정 등)이 있을 수 있다.

**질문 시점**: 유사한 컴포넌트/유틸이 1개 이상 발견되었을 때

**질문 예시**:
- "CenterSwiper와 FlatListPageSwiper 중 어떤 걸 사용할까요?"
- "기존 HeroCard 컴포넌트를 확장할까요, 별도 컴포넌트로 만들까요?"
- "formatPrice 유틸이 이미 있는데, 이걸 사용할까요?"

**AI가 틀리는 패턴**:
- 기존 카루셀이 있는데 새 카루셀을 만듦
- 공통 유틸이 있는데 로컬에 같은 로직을 중복 구현

### 1.2 데이터 출처

**왜 물어야 하는가**: 같은 UI도 데이터 출처에 따라 구현이 완전히 달라진다.

**질문 시점**: 데이터가 어디서 오는지 코드만으로 판단 불가할 때

**질문 예시**:
- "이 데이터가 SDUI 스키마에서 오나요, REST API에서 오나요?"
- "상품 목록을 서버에서 받나요, 로컬 필터링인가요?"
- "이미지 URL 형식이 CDN 경로인가요, 상대 경로인가요?"

**AI가 틀리는 패턴**:
- SDUI 데이터인데 API 호출 코드를 작성
- 서버 필터링인데 클라이언트에서 전체 데이터를 로딩

### 1.3 인터랙션/동작

**왜 물어야 하는가**: Figma는 정적 화면만 보여준다. 자동재생, 루프, 스냅, 스와이프 방향 등은 알 수 없다.

**질문 시점**: 동적 동작이 포함된 UI일 때 (카루셀, 애니메이션, 제스처)

**질문 예시**:
- "배너 자동 재생이 필요한가요? 간격은?"
- "카루셀이 무한 루프인가요, 끝에서 멈추나요?"
- "스와이프 시 스냅이 필요한가요?"
- "클릭 시 상세 페이지로 이동? 딥링크?"

**AI가 틀리는 패턴**:
- 자동재생 없는 카루셀에 자동재생 구현
- 무한 루프가 필요한데 일반 스와이프로 구현

### 1.4 구현 범위

**왜 물어야 하는가**: "구현해줘"라는 요청의 범위가 모호하다. 렌더러만인지, 에디터까지인지, 테스트까지인지.

**질문 시점**: 항상 (범위 확인은 기본)

**질문 예시**:
- "렌더러만 구현할까요, 에디터도 같이?"
- "단위 테스트도 작성할까요?"
- "타입/스키마 수정도 필요한가요?"

### 1.5 타입/디자인 불일치

**왜 물어야 하는가**: 기존 타입 정의와 새 디자인이 다를 수 있다. 임의로 타입을 변경하면 다른 곳에 영향을 준다.

**질문 시점**: 탐색 중 기존 타입과 요구사항 사이에 차이를 발견했을 때

**질문 예시**:
- "기존 HeroSlide 타입에 subtitle이 없는데, 추가할까요?"
- "현재 타입은 이미지 1장인데, 디자인은 여러 장을 보여줍니다. 타입을 배열로 변경?"
- "스키마에 overlay 관련 필드가 없는데, 추가해야 할까요?"

## 2. 실제 사례: THE_ATHLER_HERO 구현

### 배경

THE_ATHLER_HERO 엘리먼트의 렌더러와 에디터를 구현하는 요청이 들어왔다. 타입과 스키마는 이미 정의되어 있었다.

### Phase 1에서 발견한 것

- 기존 타입 `TheAthlerHeroElem`에 `slides` 배열이 정의됨
- 각 slide에 `image`, `title`, `action` 필드
- 기존 `CenterSwiper`, `FixedSwiper`, `FlatListPageSwiper` 3종 카루셀 존재
- placeholder 렌더러와 에디터가 이미 있음

### Phase 2 질문 흐름

**1차 질문** (3개):
1. 카루셀 선택 → CenterSwiper (양 옆 peek)
2. 인터랙션 → 자동재생 5초, 무한루프
3. 구현 범위 → 렌더러 + 에디터 + 테스트

**2차 질문** (2개):
1. 오버레이 그라데이션 → 하단 검정 그라데이션 있음
2. 텍스트 위치 → 이미지 위 하단 정렬

**3차 질문** (1개):
1. 에디터에서 이미지 업로드 → 기존 ImageUploader 컴포넌트 재사용

**4차 질문** (1개):
1. 슬라이드 순서 변경 → 드래그 앤 드롭 필요 여부 → 불필요, 위아래 버튼으로

### 질문이 없었다면?

| 질문 | 없었으면 벌어진 일 |
|------|-------------------|
| 카루셀 선택 | 새 카루셀을 만들었을 것 (기존 3종 무시) |
| 자동재생 여부 | 구현 안 했거나 임의 간격으로 구현 |
| 오버레이 그라데이션 | 누락되거나 잘못된 방향으로 구현 |
| 이미지 업로더 재사용 | 새 업로드 UI를 만들었을 것 |

→ **4번의 질문으로 4번의 재작업을 방지**

## 3. Figma 연동 가이드

### Figma URL 제공 시 활용 도구

| MCP 도구 | 용도 | 추출 가능 정보 |
|---------|------|---------------|
| `get_screenshot` | 화면 스크린샷 | 전체 레이아웃, 시각적 구성 |
| `get_design_context` | 디자인 토큰 | 색상, 간격, 폰트, 컴포넌트 구조 |

### Figma에서 알 수 있는 것 vs 물어봐야 하는 것

| 알 수 있는 것 (질문 불필요) | 물어봐야 하는 것 |
|---------------------------|----------------|
| 레이아웃 구조 | 자동재생 여부/간격 |
| 색상 값, 폰트 크기 | 데이터 출처 (SDUI/API) |
| 간격, 패딩 | 클릭 시 동작 (네비게이션 타겟) |
| 이미지 비율 | 무한 루프 여부 |
| 컴포넌트 개수 | 에러/로딩 상태 UI |
| 텍스트 내용 (예시) | 실제 데이터 형태 |

### Figma 활용 워크플로우

```
Figma URL 수신
  │
  ├─ get_screenshot → 전체 레이아웃 파악
  ├─ get_design_context → 디자인 토큰 추출
  │
  ▼
코드 탐색과 비교
  │ "디자인의 이 카드가 기존 HeroCard와 유사한가?"
  │ "이 간격값이 기존 디자인 시스템 토큰과 일치하는가?"
  │
  ▼
Figma에서 알 수 없는 것만 Phase 2에서 질문
```

## 5. Phase 전환 판단 기준

### Phase 1 → Phase 2 전환 조건

다음을 모두 파악했을 때 질문 단계로 전환:
- 관련 파일 목록 확인 완료
- 기존 유사 코드 존재 여부 확인
- 현재 타입/스키마 구조 파악

### Phase 2 → Phase 3 전환 조건

다음 중 해당하는 질문을 모두 완료했을 때 구현 단계로 전환:
- [ ] 재사용할 기존 코드가 결정됨
- [ ] 데이터 출처가 명확함
- [ ] 동적 인터랙션이 정의됨
- [ ] 구현 범위가 합의됨
- [ ] 타입/디자인 불일치가 해소됨

> 모든 항목이 해당되지는 않는다. 예를 들어 정적 UI면 인터랙션 질문은 불필요하다. **해당하는 항목만** 완료되면 Phase 3로 전환한다.
